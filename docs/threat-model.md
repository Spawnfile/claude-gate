# claude-gate -- Threat Model

This document describes the eight critical gaps identified during design review,
their concrete mitigations, and the gaps that remain open. It is the reference
for security review before each release.

---

## Gap 1: Prompt-injection bypassing the gate

**Problem:** A web page Claude reads tells it to run `/gate mode allow-all` or
`/gate disable`. Claude obeys; the plugin disables itself or weakens its own
policy.

**Mitigation:** All critical commands require out-of-band confirmation via the
gate-confirm CLI. When Claude attempts a critical action, the MCP tool returns
a `pending_confirmation` response with an `action_id`. The user must run
`gate-confirm <action-id>` in their actual terminal (not inside Claude). The CLI
connects to gate-mcp over the local socket, displays the pending action details,
and prompts the user with y/N. Claude has no terminal stdin access and cannot
satisfy this prompt. Critical commands are: `mode allow`, `mode allow-all`,
`disable`, `db policy <name> allow`, `setup finish`, `db remove`, and
`debug sandbox-mcp on` against prod-tagged databases.

Tokens are: session-scoped (cannot be reused across sessions), project-scoped
(cannot be reused across projects), single-use (consumed flag), and subject to
a 2-minute TTL.

**Manual review checkpoint before each release:** Attempt to make Claude satisfy
a gate-confirm prompt through prompt injection. Verify that the IPC server
rejects any `confirmation_token` not generated by a real gate-confirm CLI
invocation. Verify that tokens created in Session A are rejected in Session B.

## Gap 2: Hook failure handling

**Problem:** gate-mcp crashes, the Unix socket is unavailable, or IPC times
out. The hook must make a safe decision without the policy engine.

**Mitigation:** Tiered fail policy by resource environment. The hook reads
`~/.claude/gate/registry-cache.json` (a hook-readable snapshot written by
gate-mcp on every config change) and applies the configured fail policy:
prod=closed, dev=open, local=open, unknown=closed. If the cache is also
unavailable, the hook defaults to fail-closed for all calls. Every fallback
decision is logged to `~/.claude/gate/hook-fallback.log` for operator review.

The IPC timeout is 500ms. Calls against unknown resources with no cache entry
are blocked (fail-closed default).

**Manual review checkpoint before each release:** Kill gate-mcp mid-session
while the hook is active. Verify that prod-tagged tool calls are blocked, that
dev/local calls are allowed with warning, and that hook-fallback.log records
the event with the correct resource and env.

## Gap 3: Project-scoped vs global config

**Problem:** A plugin with global state bleeds policy from a strict production
project into a permissive local project. A user who sets strict policy for
Project A should not have that policy affect Project B.

**Mitigation:** Configuration lives at `<project>/.claude-gate/config.yaml`.
The hook resolves project root by walking up from cwd: if `.claude-gate/config.yaml`
exists, use that directory; if `.git` is found without a config, trigger
first-run setup. The walk stops at `$HOME`. Cross-project defaults live only in
`~/.claude/gate/global-defaults.yaml` and are overridden by per-project config.
Per-session state (batch tokens, pending actions) is per-session-id and never
shared across CC sessions.

**Manual review checkpoint before each release:** Open two CC sessions, each
with a different project and different policies. Verify that a tool call in
Session A uses Project A's policy and a tool call in Session B uses Project B's
policy. Verify that a batch token from Session A is rejected in Session B.

## Gap 4: permissions.deny precedence

**Problem:** If a user has `permissions.deny` rules in settings.json that should
block a tool call, does claude-gate's ALLOW decision bypass those rules?

**Mitigation:** Claude Code's permission evaluation order is:
deny rules -> PreToolUse hook -> ask rules -> allow rules -> user prompt.
If `permissions.deny` matches, the hook never runs. claude-gate only runs after
deny rules pass. If the hook says ALLOW, downstream `permissions.allow` may
still require a user prompt. claude-gate does not override deny rules and does
not replace CC's permission hierarchy; it operates as one layer within it.

This is documented explicitly: claude-gate operates inside CC's permission
hierarchy. It is layered on top of, not replacing, deny rules.

**Manual review checkpoint before each release:** Add a `permissions.deny` rule
for a tool. Verify the hook does not run for that tool (confirm via hook-fallback
absence or hook invocation log). Verify that a claude-gate ALLOW for a different
tool does not suppress a CC-level user prompt for the same tool.

## Gap 5: Performance under bulk operations

**Problem:** A 1,000-statement migration script adds 50-200 seconds of overhead
if each call goes through the full 7-stage pipeline.

**Mitigation:** Batch session approve tokens. The user runs
`/gate batch-approve sql:supabase_dev for=10min count=1000` to create a
session-scoped token. Stage 5 of the pipeline checks active tokens; matching
calls skip stages 2-6 and return ALLOW immediately. Each match decrements the
remaining count and writes a thin audit entry. CRIT-risk operations (DROP,
TRUNCATE, etc.) are never covered by batch tokens; they go through full
evaluation regardless.

Batch-approve is a future slash command surface. The session token
infrastructure is already in place.

**Manual review checkpoint before each release:** Verify that a DROP TABLE
issued while a batch token is active is still evaluated by the full pipeline
and produces DENY under strict/confirm policy. Verify that the token is
decremented only for non-CRIT calls.

## Gap 6: Discovery confidence

**Problem:** Heuristic discovery may miss databases. If the user assumes
coverage is complete when it is not, they have a false sense of security.

**Mitigation:** Confidence scoring and explicit coverage reporting. Each
detection carries a confidence score in [0.0, 1.0]. The setup wizard requires
user disambiguation for any detection below 0.7. The `/gate db audit-coverage`
command shows exactly which scanners ran, which files were found, and explicitly
lists what could not be discovered (runtime connection strings, shell rc env
vars, cloud-managed databases without local config files). Discovery is honest
about its own limits.

**Manual review checkpoint before each release:** Run discovery against the
test fixture `repo-tricky-names` and verify that any DB with confidence below
0.7 is flagged for disambiguation. Verify that the audit-coverage output lists
docker-compose and ORM scanners as pending and not as completed.

## Gap 7: Adversarial rule pack updates

**Problem:** A plugin update changes default risk classifications in a way that
breaks user workflows or silently weakens protection.

**Mitigation:** Rule pack versions are pinned in `config.yaml` under
`rule_packs.sql.pinned_version`. Plugin updates do not auto-upgrade pinned
versions. The `/gate update review` command shows a diff between the pinned and
shipped versions before the user accepts. The user must explicitly run
`/gate update accept sql <version>` to apply an upgrade. No silent breakage on
`claude plugins update`.

The sql rule pack ships at pinned version 1.0.0.

**Manual review checkpoint before each release:** Verify that a plugin install
on a project with a pinned version does not silently change the active rule pack.
Verify that `/gate update review` shows the correct diff when shipped and pinned
versions differ. Verify that no update is applied without an explicit accept.

## Gap 8: Audit log integrity

**Problem:** The audit log is a plain JSONL file. Anyone with filesystem access
can edit it, making it unreliable for post-incident review.

**Mitigation:** SHA-256 hash chain. Each audit entry contains `prev_hash` and
`this_hash`, where:

    this_hash = SHA256(canonical_json(entry minus this_hash) || prev_hash)

`/gate audit verify` walks the full chain and reports the first inconsistency
if the chain is broken. Rotation preserves cross-file chain integrity: the first
entry in a new file after rotation references the final hash of the archived
file.

The OS-level append-only flag (`chattr +a` on Linux, `chflags uappnd` on macOS)
is applied at deploy time, not automatically by the plugin. See the
"Known gaps not closed" section below.

**Manual review checkpoint before each release:** Manually edit a line in
audit.jsonl and run `/gate audit verify`. Verify that the tamper is detected
at the correct line number. Verify that rotation-boundary verification works
by running `/gate audit verify --include-archived` across a rotated pair.

## Known gaps not closed

These are documented known limitations, not omissions. Each has a planned fix
in a future plan or phase.

**Prompt injection of non-critical commands.** The gate-confirm defense applies
only to the critical command list. Non-critical commands (e.g., `/gate status`,
`/gate db list`) can be invoked by Claude in response to injected instructions.
These commands are read-only or session-scoped and cannot weaken policy, but
the injection surface exists.

**Discovery limited to env files and .mcp.json.** Docker/Compose, ORM config
scanners, and source-code scanners are planned for a future version. Any
database whose connection string is not in .env files or .mcp.json is not
discovered and not governed.

**Hook fallback is heuristic-only, no SQL parser.** When gate-mcp is
unreachable and the hook falls back to the registry-cache, it applies only
env-tiered fail policy (block prod, allow dev). The full SQL parser is not
available in the fallback path; there is no risk classification in fallback.

**OS-level append-only flag on audit.jsonl deferred to deploy time.** The
`chattr +a` / `chflags uappnd` application is a deployment step, not applied
automatically. The hash chain provides tamper detection, but the file is not
append-only at the OS level.

**Critical-action flow uses no confirmation token in the gate_decide path.**
The flow is: the MCP tool returns an action_id, gate-confirm sets a confirmed
flag over IPC, and the next MCP tool call reads the flag. No token is issued to
Claude; the action_id is the sole identifier. A typed confirmation token for
stronger binding is planned.

### No external API calls

claude-gate makes every decision locally and deterministically: SQL parsing,
risk classification, and per-resource policy lookup. It never sends any data
to Anthropic or any other external service. (An earlier `second_opinion`
stage that called Anthropic's Haiku model was removed; see CHANGELOG 0.6.0.)
